# 固定版本归档与离线复核

本轮补齐“报告与记录共同留存”的最后一环。正式项目有“版本归档”，项目列表的同一入口可查看所有本机版本。演示入口为 `#/report?view=archive`；通用校验入口为 `#/projects/archives`，均不依赖验收项目 UUID。

## 设计选择

将归档版本与工作项目分开。工作项目可以继续追加评测、裁决和结论；已经生成的归档保留原来的报告、主包、规则题库快照、修订历史、同步审计与原图字节，不被后续修改覆盖。页面比较内容摘要，提示“与当前工作数据一致”或“工作数据已变化，旧版本保留”。这是按版本留存成果，没有把可继续编辑的工作项目全局锁成不可修改状态。

两种类型：

- **阶段快照**：配置必须有效且规则已确认，评测和质检可未完成；所有缺口写入文件，报告明确标为阶段快照。
- **最终归档**：当前配置范围的全部检查通过，负责人确认范围、功能/授权摘要与结论，且原图实际读取校验成功后才可创建。它不是完成真实课程评测的替代证明。

配置未齐、题量与计划不符、规则未确认的草稿，使用原有“项目备份”；不能生成一个无法走阶段同步恢复流程的版本归档。

若未配置自家，最终归档仅代表已声明的真实竞品范围，不声称完成原四产品方案。已配置自家时，逐题 GSB 必须全部形成有效判断；模拟比较单列。归档中明确保存真实/模拟产品 ID、题量和自家是否在范围内，不提供隐藏范围删减按钮。

## 操作流程

1. 完成项目配置，并确认当前评测范围。
2. 打开“版本归档”，选择阶段快照或最终归档、统计口径与负责人，填写版本说明。
3. 最终归档需负责人确认功能/授权依据及结论。系统检查数据、质检、联合排名、备注、案例和最终引用；原图在生成时逐张校验。
4. 生成后，本机独立保留该版本的全部文件。下载每一项，放在同一个文件夹保存。
5. 重新选择全套文件，进行离线复核。校验通过可再次留存只读版本；重复留存同 ID/同摘要不会增加记录，同 ID/不同内容拒绝覆盖。
6. 要恢复或合并工作项目，将其中 `.eval.json` 与全部 ZIP 交给现有“阶段同步”预览并确认。校验归档或留存只读版本本身不会改动工作项目。

归档文件组包括：

| 文件 | 内容 |
| --- | --- |
| `<id>.archive.json` | 总清单、模式、负责人、确认项、范围、检查结果、源数据摘要、文件大小与 SHA-256 |
| `<id>.eval.json` | 可恢复的完整项目主包清单，绑定规则题库快照、原记录、质量判断及审计 |
| `<id>.part-NNN.zip` | 按现有 40 MiB 目标 / 50 MiB 硬上限分包的原图，按 SHA-256 去重 |
| `<id>.report.json` | 固定当时数据与口径的报告明细、检查与证据引用 |
| `<id>.report.md` | 相同版本的可阅读报告 |

它是一组可校验文件，不是将所有原图塞进一个不受控大小的 ZIP。原图格式与阶段包上限沿用现有协议；总清单最大 1 MiB、报告 JSON 最大 20 MiB、Markdown 最大 2 MiB。大规模上限仍是技术限制，不代表已完成同规模压力验证。

## 完整性与并发

生成从一个 IndexedDB 读事务获取项目、记录、快照和同步审计。打包前比较页面看到的内容版本；全部文件生成后，在写事务中再次比对源数据和审计，期间出现修改即中止保存。新记录使用 `add`，没有原地修改历史归档的接口。空间不足导致事务失败时，不修改工作项目或已有归档。

新数据库版本为 4，新增 `archives` 对象仓库。保存实际文件 Blob，后续下载不依赖重新运行评分或重新拼接旧文件。相应代价是额外本机空间；应将各版本完整文件组另存磁盘。普通项目 JSON 备份和阶段主包不递归包含所有独立归档版本。

复核不只检查外层哈希，还会：

- 核对文件数量、名称、大小、角色与 SHA-256，拒绝缺包、混包、重名和额外文件。
- 沿用阶段 ZIP 的格式、CRC、每张原图字节、快照与引用检查。
- 比较冻结的项目、范围、统计口径和内容摘要。
- 从冻结主包重新计算当前版本的报告和检查，逐项比对报告 JSON 与 Markdown。不能只改一个外层标签，就把未完成的快照改成最终归档。

本轮进一步检查全部已分配质检任务形成有效判断，复评/复查题目不重复，以及最终裁决仍引用当前初评与最新独立判断。工作数据的本地修订编号、更新时间、恢复来源和读取顺序，不单独造成“内容已变化”的误报。

## 独立评审隔离

归档含原标签、分数和讨论，不能导入已有该项目独立评审空间的站点。反过来，站点已存有该项目完整归档时，不能再接收该项目独立盲评任务。两向检查包含事务内检查，归档只读存储不会成为原判断进入独立空间的旁路。

姓名和勾选参与人不是身份认证。哈希校验用于发现损坏、混包和内容不一致，不是评测员数字签名，也不能证明三人真实完成了流程。

## 版本与后续边界

归档清单声明 schema 1 和 `calculationVersion: ecommerce-v1`。不支持的计算版本会明确拒绝校验。以后改评分、报告结构或检查文案，需要升级计算版本并保留对应旧版核验逻辑，不能默默拿新规则重算旧归档。已经留存的文件字节不会随代码改版改变。

当前功能检查仍是人工文字摘要并由负责人确认，尚未拆成逐产品结构化检查项。报告不内嵌案例图片，也未提供 PDF/雷达图版本。没有云端同步、账号认证、GitHub 仓库推送或公开部署。

## 验证

- 自动测试累计 **207 项通过、0 失败**；生产构建和 TypeScript 检查通过。
- 新增 17 项测试：完整 50 题合成工作流可以生成并复核最终归档；未完成、试跑、缺确认与无效配置被阻止；缺图/损坏中止；工作后续修改不改变旧文件；缺包/混包/重名、重签后篡改报告、伪装最终归档和不支持的计算版本被拒绝；GSB 范围与全部质检覆盖被检查。
- 浏览器：50 题界面演示生成阶段快照，实际下载 5 个文件并重新上传，复核通过；其未完成质检无法点击最终归档。
- 正式存储区：两题功能验收项目生成阶段快照，刷新后仍可选择并下载。之后修改工作报告结论，旧版本提示数据已变化；独立读取下载文件确认旧结论和文件 SHA-256 保留。
- 从不带项目 ID 的全局入口复核正式快照并重复留存，仍只有同一版本，工作项目保持新结论。上述浏览器数据全部是功能验收或合成示例，未替代真实三人、50 题课程评测。

最终归档正向条件由完整合成工作流自动测试覆盖；浏览器实际验证的是有缺口的阶段快照与最终归档阻止路径。未进行真实多人设备全规模归档验收或存储配额故障注入。
