# 阶段同步：准备分发、初评提交与主包汇总

本轮支持三名评测员各自在浏览器中采集初评，再由负责人通过文件集中合并。它延续正式项目的本地评分、原图保存和修订留痕，并新增可校验的分包传递、导入预览、冲突处理与同步收据。

本文记录初评同步阶段的准备包、初评提交包和汇总主包。后续已接入[独立评审与质量裁决](10-quality-workflow.md)、[联合排名与报告](11-joint-review-and-report.md)及[固定版本归档](12-version-archive.md)；完整流程应结合这些文档阅读。[完整阶段协议](04-sync-protocol.md)还包含尚未全部实现的设计。

## 1. 三种数据包

| 类型 | 用途 | 当前内容与边界 |
| --- | --- | --- |
| 准备分发包 `assignment` | 负责人让三人从同一项目开始 | 已确认的规则、完整题库、成员与产品分工、参考图；不包含初评、走查、体验分或输出图 |
| 我的初评提交包 `submission` | 评测员交回自己负责的产品 | 只携带所选发送成员负责产品的评测修订、输出图、走查及体验记录，保留必要的共同项目定义和参考图；不携带同步历史审计 |
| 汇总主包 `baseline` | 负责人发布当前合并结果或归档 | 全部产品的当前记录、原图、快照与历史同步审计；包含原始标签和备注，不是盲复评包 |

成员选择是本地工作流标识，没有账号登录或身份认证。工具按声明的发送成员和产品负责人检查提交范围，不能验证操作者本人是谁。

## 2. 推荐的三人流程

1. **负责人建立项目。** 补齐成员、三个真实竞品名称与版本、负责人、计划题量、题库、参考图和规则。三人必须共用同一项目 ID，不要各自新建三个名称相同的项目。
2. **负责人分发准备包。** 在正式项目“团队同步”选择准备分发包及发送成员，生成并下载清单和所有分包，交给另外两人。准备信息需先通过校验；分发后评测范围冻结。
3. **评测员导入。** 在正式项目入口打开团队数据导入，一次选择清单与全部 ZIP，查看项目、发送人、产品范围、新增、重复及阻断项，确认后建立本机同 ID 项目。负责人可继续使用原本机项目，无需重复导入自己的准备包。
4. **三人分别采集。** 各自仅操作分配产品，按同一题库保存首次全部输出，完成逐图检查、最佳图标签、耗时及失败记录，再补走查、费用、体验分和商用授权。草稿与已提交状态分别保留。
5. **评测员提交。** 选择“我的初评提交包”和自己的成员身份，将生成的完整文件集交给负责人。未完成的题目仍是缺口，导出文件本身不等于任务全部完成。
6. **负责人检查并合并。** 分别导入三人的提交包。查看阻断项及冲突；有分歧时逐项选择保留本机或采用导入，并填写处理成员和依据。确认后事务写入，实际得分按合并后的有效记录重新计算。
7. **负责人发布主包。** 完成当前汇总后导出汇总主包，保留一份完整文件集，也可分发给三人。接收者可合入本机同 ID 项目，但主包会揭示初评及历史判断，不应用作未来独立盲评的素材入口。

可以在尚未完成全部题目时阶段性交接，汇总会继续显示未完成题量。三人的提交顺序不会改变无冲突记录的结果；重复导入不会增加相同修订的数量。

## 3. 文件组成与下载

每次导出生成一个唯一包 ID，并产生：

- `<包ID>.eval.json`：项目、记录、快照、范围、媒体摘要和分包清单；主包还包含历史审计。
- `<包ID>.part-001.zip` 等：承载原图的 ZIP 分包。没有原图时可以只有清单。

页面逐个提供下载，需确认清单和每个分包都已经下载。下载触发状态不能证明文件已成功保存到磁盘。传递时保留完整文件集和原文件名；导入时一次选择同一包的清单及全部分包。无需先解压，也不要重新打包、改名或混入其他包的 ZIP。

媒体按 SHA-256 去重，相同内容只传一份，但题目与产品的图片引用分别保留。原图以原始内容存放，分包主要用于限制单个传递文件的大小，不依赖压缩减少图片体积。

## 4. 导入检查与冲突处理

导入先检查格式、文件清单、分包摘要、原图摘要、大小与类型，再核对项目身份、成员和产品定义、规则与题库快照、发送人的产品范围以及图片引用。缺包、损坏、同 ID 不同内容或规则不兼容会阻止写入，需修正来源后重新导出。

修订由父子关系决定，时间戳只用于追溯。相同 ID 且相同内容是重复；完整线性祖先或后继可自动接入；独立根或两端从共同父版本产生不同分支时，需要人工处理。联合后仍缺父修订时阻断导入，不能偷偷视为新根。

采用对方评测判断时，不删除本机原始链，而是在本机当前头之后生成新修订，复制所选对方判断，并记录处理人、来源包、来源修订和依据。对方原冲突链保存在同步收据中，不并入当前生效链。保留本机时，不将对方冲突链接入当前链。

产品费用、商用授权及证据、走查和整体体验作为一组辅助信息处理。双方都有不同的非空信息时，需明确选择整组；不会按时间自动拼出一个混合版本。默认空信息可接入一方的有效信息，空提交也不会抹掉本机已有结果。

预览后若本机数据发生变化，确认导入会被拒绝，需重新检查文件。通过检查后在一个 IndexedDB 事务内写入，出现空间不足、ID 冲突或其他写入失败时回滚。页面显示的“合并冲突处理”只解决数据版本选择，不等于已实现独立复评后的质量裁决。

## 5. 同步收据与主包

收据保留包 ID、发送成员、导入时间、新增及重复统计、冲突双方、处理选择、依据、导入原始数据与合并前本机数据。主包携带已有审计，便于后续追溯；这些记录可能包含已经不再生效的原始判断。

同包重复导入按幂等规则处理，不重复新增记录。同 ID 的图片清单或记录内容被改写时拒绝覆盖。同步收据是本地审计材料，尚无数字签名、认证成员或服务器端可信时间，不能据此证明操作者身份或未曾查看其他结果。

## 6. 容量与运行边界

| 项目 | 当前技术限制 |
| --- | --- |
| ZIP 默认目标大小 | 每份 40 MiB |
| ZIP 硬上限 | 每份 50 MiB |
| 单张原图 | 25 MiB |
| `.eval.json` 元数据清单 | 10 MiB，包含主包历史审计 |
| ZIP 数量 | 最多 256 份 |
| 去重后原图总量 | 最多 8 GiB，并同时受分包数量约束 |

以上是格式和代码中的技术边界，不表示已完成 8 GiB 或 256 分包的压力验证。实际可处理规模还受设备、浏览器可用内存、磁盘和 IndexedDB 配额影响；主包审计持续增长也可能先触及 10 MiB 清单限制。

原有 JSON 完整备份仍适用于原图合计 75 MB 内的项目，恢复只接受本机不存在的项目 ID，不合并。阶段包用于同项目的交接和合并，二者不可混用；演示备份也不能作为正式阶段包导入。

所有数据仍在当前浏览器配置与 origin 的 IndexedDB 中，不会自动同步。阶段文件由人主动传递；网页部署和 GitHub 源码不会托管这些记录。当前功能验证使用小规模验收数据，开展课程的真实 50 题评测仍需真实产品版本、完整题库、参考图与实际输出。
