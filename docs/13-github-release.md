## 首次发布

1. 准备一个空仓库，确定公开仓库地址、许可证及提交身份。若仓库已有内容，先检查已有历史和文件，再接入，不能覆盖已有项目。
2. 在本项目目录初始化 Git，将源码、锁文件、方案和文档作为初始提交，关联目标远程仓库后推送。整个上层对话目录、测试下载和导出记录不进入仓库。
3. 在仓库 Settings → Pages，将 Build and deployment 的 Source 设为 **GitHub Actions**。
4. 查看 **Check and publish Pages** 的 check 和 deploy 是否成功。部署地址以 Actions 返回的 `page_url` 为准。
5. 在最终网址验证首页、正式项目入口、报告演示、归档演示和图片。用同一个网址刷新后重新打开本机项目；再用另一个浏览器确认没有自动出现前一浏览器的数据。

配置参考 [GitHub Pages 自定义工作流](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages) 与 [Vite 静态部署](https://vite.dev/guide/static-deploy.html#github-pages)。项目保留 `base: './'`，资源使用相对路径和 hash 导航；默认域名和仓库子目录不需写死仓库名。未来若改为 history 导航、绝对路径或自定义路由，需要重新验证子目录部署。

工作流使用声明的 Node.js 与 pnpm，锁定依赖安装，先测试再构建，再上传静态产物。普通分支和外部 PR 无部署权限。Pages 需要的权限只授予 deploy 任务；无需在源码内放个人访问令牌。

工作流只能发布静态网站，三人的评测记录仍要通过文件交接。配置完成后，任何人可以打开界面；个人本机项目不会随站点公开。**Pages 同一域名下的多个仓库路径属于同一个 origin**，路径不提供 IndexedDB 隔离；独立评审使用不同浏览器配置，不能仅靠换仓库路径。

从本机网址切到公开网址也是数据区变化。先在本机下载完整主包及全部分包，到线上导入并核对；旧项目在原浏览器原地址中仍保留。归档文件组需单独保存。

## 三人试评：先用独立的 5 题项目

| 阶段 | 负责人 | 另外两名成员 | 通过标准 |
| --- | --- | --- | --- |
| 建立试跑 | 建新项目，计划题量设为 5，填写三人、产品版本与分工、确认规则 | 确认各自负责产品 | 共用同一项目 ID；不各自新建同名项目 |
| 准备分发 | 导出准备包，保存全部文件 | 在各自电脑同一网站导入 | 项目、题库、规则与分工一致 |
| 采集与校准 | 汇总共同 5 题的原图与最佳图草稿，固定校准批次 | 收集首次输出；在单独浏览器配置完成定向独立任务 | 独立包不显示原判断；返回包可回收 |
| 初评汇总 | 导入两人的本人提交包并检查缺口 | 完成分配产品后导出本人提交包 | 原图可打开、修订数量正确；重导同包不重复增加 |
| 复评与比较 | 固定交叉复评，收回并处理分歧；配置自家时验证 GSB | 在独立配置中完成任务并回传 | 一致率有分母；平局进入 GSB 分母，无法判断不进入 |
| 留存 | 填写报告，生成阶段快照并下载全组文件 | 协助核对样例图片和结论 | 刷新后记录保留；重选全组文件可通过归档复核 |

5 题项目会标记试跑；交叉复评不能替代正式每产品 10 题，不应触发正式全量复查。联合排名也不能作为完整 50 题结论。试评验收目标是三台电脑的数据交接与操作可用性，生成**阶段快照**即可。

独立任务入口为 `#/projects/independent`。每人把初评和独立评审放在不同的浏览器配置中，沿用正常浏览器持久存储，避免将关闭后会清空的数据区作为长期保存位置。不要先把完整主包导入独立评审配置；系统会拒绝同项目混用。

试跑后如需调整题库、成员或产品范围、真实/模拟属性及评分规则，另建正式 50 题项目。开始评测、分发或固定质检后，这些范围已冻结；现有成员姓名及产品名称、版本、竞品角色、负责人仍可更正。试跑所得图片和分数不要混入正式课程报告。

## 正式评测前还需准备

- 完整 50 题、参考素材、验收要求及场景/品类/难度分布。
- 3 个实际竞品及准确版本、账号方案和生成设置；模拟自家仍明确标记模拟。
- 每人负责产品、时间安排、共同校准时间和交接渠道。
- 首次出图的全部输出及耗时、费用和商用授权依据。

代码内的题目与示范图用于交互演示。现有测试通过不等于三位真实评测员已完成上述试评，也不等于已获得真实产品结论。
